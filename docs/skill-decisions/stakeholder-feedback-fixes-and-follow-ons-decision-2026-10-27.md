# Stakeholder feedback is sorted into fixes and new asks, and new asks go to a follow-on once the build has started (decision record, 2026-10-27)

Maintainer notes for `skills/assumptions-document-feedback/SKILL.md` (Step 1a, Step 6, Step 8) and the matching lines in `phase-split`, `implement-from-requirements`, `implementation-lifecycle`, `initiative-breakdown`, `prd-writing-standards`, `continuation-prompt` and `using-the-enso-method`, plus the README and `how-the-enso-method-works.md`. This file is outside every skill directory and is not loaded by any skill.

## The problem

- **Feedback arrives late, and the skill folded all of it into the PRD.** Stakeholders answer on their own schedule, often when the build is nearly or fully done. The skill sent every stated change to a criterion or mockup straight into the PRD, with no test of whether it corrected the PRD or asked for something new. A round of answers on a delivered PRD typically mixes corrections with requests that contradict the PRD's explicit exclusions. Folded in together, those requests can add several phases to a finished plan and reshape PRDs that other work depends on.
- **The new functionality got no review of its own.** Asks folded in as "corrections" got no fresh mockups, no new assumptions register and no stakeholder review package. The method's review machinery runs per PRD, and these asks never became one.
- **Code routing ended at the user.** When the work was complete, the skill named each change as an action item for the user to run through `implement-from-discovery`. On a PRD large enough to need phases, "go make the code match the amended PRD" is not a unit any session can build, so the phases had to be planned by hand.
- **The user cannot make these calls well.** Many chats run in parallel, and the person routing feedback does not hold the whole picture. The session can see the documents, the code and the other work in flight. Every call is the session's, recorded in one line.

## Options considered

1. **Keep folding everything in, and only add phase routing.** Rejected: it fixes the hand-routing but keeps growing a nearly finished PRD mid-build, and new asks still get no review of their own.
2. **Every new ask becomes its own PRD.** Rejected: multiple rounds, each with a few asks, would multiply PRDs. The unit is one follow-on per PRD that collects new asks until its own build starts, so the count grows with releases, not requests.
3. **Decide by size alone.** Rejected: a large correction is still a correction. The test is intent: does it make the PRD deliver what it set out to deliver, or change what it set out to deliver?
4. **Chosen:** sort each change into a fix or a new ask. Fixes always amend the PRD. New asks amend it too until the build starts; after that, only minor ones do, and the rest go to one follow-on.

## Decisions and why

- **The switch is "the build has started", not "the change is new".** Before any build, folding in a new ask is ordinary requirements work, and the PRD's own refinement gives it mockups and assumptions. The started test is a committed phase plan, a Closed line, or a commit or session log showing a build, looked for on the shared branch and in every local worktree. Nothing is published when a build starts, and adding such a marker would mean pushing to the shared branch at the start of every build, which the push rules hold for the user. A wrong guess is caught anyway: an ask folded into a PRD whose build was invisible sits in no phase, and `delivery-audit` finds it unbuilt.
- **"Minor" is four checkable tests,** not a judgment of size: it serves the stated outcome and reverses nothing; it needs no new screen and no new stakeholder assumption; it changes no other PRD; and all of the round's minor asks fit one phase. The second test catches exactly the asks that would otherwise skip review.
- **An existing home beats a new follow-on.** An ask within another PRD's stated outcome is feedback on that PRD. This, and the one-open-follow-on rule, keep the PRD count from ballooning.
- **Reversals have a fixed order of outcomes.** Behavior not built yet is not built (its criterion is retired). Built behavior that leaves nothing behind ships, and the follow-on replaces it. Built behavior that leaves records, external writes, wasted human effort or a dependent contract is switched off. In each case, if removing it would gut the PRD's stated outcome, the replacement is pulled in as a fix. Shipping changed behavior later is normal iteration; leaving data or effort that a later release must clean up is the harm to avoid.
- **A removal with nothing to replace it makes no follow-on.** It is retired, or removed as a fix if built; a follow-on with nothing to build would waste a PRD-writing session.
- **Mid-build fixes go into the next unstarted planned phase, not the end of the plan.** Appending them would let later phases build on behavior already known to be wrong. This reuses the existing carried-forward rule for gaps. A phase a session is building is never edited, since that session has already loaded its document. Feedback phases, in the completion-phase form, are for when no unstarted planned phase is left, and for an unsplit PRD whose build has started. An unsplit PRD gets no delivery audit by default, so when its build state is unclear it counts as started.
- **The feedback chat does not write the follow-on.** It records the follow-on (a planned PRD row and contracts entry in an initiative, or a change directory with a scope file outside one), saves the stakeholder's words, and hands off with a prompt. Writing a PRD with mockups and assumptions is a session of its own, and writing it alongside the first release's build gets the stakeholder's review of the new asks back sooner. A `**Follow-on to:**` line, in the entry or scope file and later under the PRD's H1, is how the next round finds the open follow-on.
- **Rules that forbid creating work unasked, or that would fold the follow-on back in, get one exception each,** for follow-ons only: adding a planned PRD and the size band's merge-small-entries rule (`initiative-breakdown`), creating a change directory and amending by default (`prd-writing-standards`, `using-the-enso-method`), and a prompt for another track (`continuation-prompt`). A stakeholder's request is not a discovery. `implement-from-discovery` is deliberately unchanged here; whether it should write requirements first is a separate decision.
