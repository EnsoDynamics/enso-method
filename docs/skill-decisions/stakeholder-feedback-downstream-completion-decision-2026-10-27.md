# A feedback round finishes every PRD it reaches, and checks each once instead of refining it again (decision record, 2026-10-27)

Maintainer notes for `skills/assumptions-document-feedback/SKILL.md` (Steps 4a, 5, 5a and 8, and the Output Format) and the matching lines in `using-the-enso-method`, `phase-split`, `implement-from-requirements`, `autonomous-prd-refinement`, `autonomous-design-refinement`, `deliverable-review` and `continuation-prompt`, plus the README and `how-the-enso-method-works.md`. This file is outside every skill directory and is not loaded by any skill.

## The problem

- **A change kept in one PRD can break the PRDs that consume it.** The skill sent each change to the PRD that owns it (Step 1a), but never asked which other PRDs consume what the change altered. When a round reshapes a shared record or rule, the written PRDs downstream are left designed against the old contract, and at most a line in the round's report says so.
- **That line lives in the wrong place.** It sits in the source PRD's report. A session opening a downstream PRD for its next stage sees documents ready for that stage, and works against a contract already known to be wrong.
- **Finishing the job falls to the user as a stack of prompts.** Each affected PRD comes back as several chats, one per skill, each needing the user to sequence it and explain which feedback it continues. With several PRDs that is the user running a project, which is the work the method exists to take off them.
- **The refinements are the wrong tool for an amendment.** The PRD and design refinements take a draft to ready over many passes. An amendment changes a bounded part of documents that were already ready, to match a decision the round already made. Running a refinement again restarts a stage the PRD had passed, to find questions a single scoped check finds.

## Options considered

1. **A new skill to amend an existing PRD**, called by the feedback skill for each affected PRD. Rejected: the feedback skill already amends requirements, so the new skill would split one operation between two skills with near-synonym names, and invite the same "run this skill, then that one" handoff the change exists to remove. The real boundary is between work done once per round (interpreting the reply) and work done once per affected PRD (amending it), and that is a step boundary inside one skill, with the per-PRD part run by a subagent.
2. **Better handoffs only**: record the remaining steps and give the user one prompt at a time. Rejected: it reduces the clutter of prompts without reducing the chats, and leaves nobody responsible for finishing the whole round.
3. **Have the feedback skill run the refinement skills on each affected PRD.** Rejected: each refinement is itself an orchestrator of subagents running for hours, so the round would nest orchestrators inside orchestrators, which no one can watch or bound, and which some harnesses do not allow at all. It would also restart stages the PRDs had already passed.
4. **Chosen:** the round finishes every PRD it reaches, owners and consumers, each amended by one writer subagent and given one fresh check by one reviewer, all launched from the feedback chat, one level deep.

## Decisions and why

- **Consumers are found from what the initiative already records.** The Seams table names who receives each contract, and criterion labels find the PRDs that cite a changed criterion. A consumer still planned needs nothing beyond its updated seam row and entry, since its PRD will be written from them. A change sent to a follow-on reaches no consumer yet: the source PRD still ships the old behavior until the follow-on is built, and the follow-on's own Changes and Replaces lines carry it to consumers when it is written.
- **Each list is written into the PRD's own directory before anything is amended,** as one block per round in a pending-changes file, the reviewed PRD included. The file is what any session opening that PRD sees, and what lets the round resume after an interruption without a list addressed to the user. Each block records the round's base commit, so the check can always find the round's diff even when part of it was committed in between, and the PRD's build state, so its writer can route code changes without redoing the evidence search. A later round adds a block rather than replacing one. A block is removed in the change that finishes its PRD, like the follow-on scope file and the refinement state files. The refinements, phase planning and the build all apply a pending file before their own work, so a block left behind is never planned or built around.
- **Resuming is a defined entry, not a rerun.** A run that finds a pending file skips interpretation, which the round already did, and acts on each block's status. That is the same procedure for an interrupted round, a PRD reached from the map or from another skill, and a chat of its own.
- **One check, not a refinement, for every amended PRD whose documents had been refined,** the reviewed PRD included, which before this change got no required check. A fresh `deliverable-review` scoped to the PRD's diff since the base asks whether the PRD now agrees with what it consumes and whether a builder would still face a judgment call, under the design refinement's scope gate. One more delta check follows only when the fixes changed a rule or interface, and the check ends there, an exception `deliverable-review` names to its usual end on a full round. What a third pass would find, phase planning and the build settle as assumptions, and the delivery audit backstops.
- **No limit on how many PRDs a round finishes.** Each writer and reviewer works in its own context and the feedback chat reads only their reports, so neither the count of PRDs nor the length of a list is what fills the session. A PRD goes to a chat of its own only when it must make design decisions the round did not make, named in its block. That chat runs the same skill: it makes those decisions first, researched and written into the design, then amends and checks the PRD like any other, so it cannot loop back to the same open decisions.
- **Every subagent is launched by the feedback chat.** Writers and reviewers launch none of their own, writers on different PRDs can run side by side, and the shared initiative files are edited by the feedback chat alone so no two writers touch one file. A writer never starts on a PRD another session is already working on; the block waits for that session, which applies it first.
- **A PRD the round finished is back at the stage it had reached.** Its next stage is its own track, not a prompt from the round. The round's prompts stay limited to work that is a job of its own: writing a follow-on, building feedback phases on a finished plan, and the rare PRD sent to a chat of its own.
