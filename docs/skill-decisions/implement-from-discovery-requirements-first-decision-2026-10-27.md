# Ad hoc changes are written into the requirements first, and implement-from-discovery decides where (decision record, 2026-10-27)

Maintainer notes for `skills/implement-from-discovery/SKILL.md` (When to Use, Phase 1, Phase 4, Phase 8, Rules) and the matching lines in `prd-writing-standards`, `implementation-lifecycle`, `phase-split` and `using-the-enso-method`, plus the README and `how-the-enso-method-works.md`. This file is outside every skill directory and is not loaded by any skill.

## The problem

- **Requirements first held only for changes small enough to amend.** Since `1d79b09` the skill amended the owning PRD before writing code. Anything bigger (a new outcome, a change spanning PRDs, a component with no PRD) went back to the user to open a change directory, and the session was barred from creating one. In practice the user stopped to make a call the session was better placed to make, or the change was built with no requirements behind it.
- **There was no stated line for "too small to write down".** "A bug needs no manufactured requirement edit" covered one case; everything else was judgment. That allows two failures: documents that record every tweak until neither people nor agents can read them, and small business-rule changes that slip through because they are small.
- **Stakeholder feedback had just gained a sorting rule** (fix, minor new ask, follow-on). Ad hoc changes reach the same documents and had none.

## Options considered

1. **Keep the hand-back.** Rejected: the method decides. Someone running many chats in parallel cannot see the documents, the code and the work in flight the way the session can.
2. **Every change above trivial gets its own change PRD.** Rejected: change PRDs everywhere, and requirements fragmented across many directories where one living PRD reads better.
3. **Decide by the size of the change.** Rejected: size is the wrong axis. A rewrite of retry handling can leave every document true; a one-character change to a refund rate makes one wrong. A size threshold lets through exactly the dangerous case, a small business-rule change nobody records.
4. **Chosen:** three levels (nothing, an amendment, a change PRD), decided first by whether the documents stay true and then by the same test stakeholder feedback uses.

## Decisions and why

- **Level 1, nothing written, when the documents stay true and no business rule changes.** That covers a bug the documents already rule out, a technical change that leaves the design's recorded decisions intact, and wording, layout or ordering the documents don't specify. The commit message is the record. This is the line against bloat: detail finer than the documents already use stays out.
- **A business rule is always written down, but as part of the rule it belongs to.** Small rules are the ones that drift unnoticed. Restating the rule, with a table when cases multiply, keeps the criterion readable under the existing readability rules.
- **Choosing between an amendment and a change PRD reuses `assumptions-document-feedback` Step 1a,** cited rather than copied so the two skills cannot drift apart. Fixes amend; new behavior amends when it is minor; anything else gets a change PRD. What this skill changes is almost always already built, so the rules for a started build apply. Two conditions differ, each for a real difference between the situations:
  - **An assumption is allowed.** In feedback, needing a new assumption marks an under-specified ask that deserves its own review. Here Phase 3 declares one for every business choice below 95%, routinely. Keeping the condition would create a change PRD for every assumption.
  - **The size condition is one change fitting one session,** not a round's asks fitting one phase.
- **A change PRD that changes an existing PRD's behavior is that PRD's follow-on.** One concept across both skills, the same `Follow-on to:` line, and the same one-open-follow-on rule: a change joins an open follow-on whose build hasn't started, instead of creating a second, and is built with it.
- **Change PRDs are named for the behavior area they govern, not the fix.** The next change in that area then finds an owner and amends it. This answers the main risk. In repos whose components predate the method, a business-rule change has no owning PRD, and naming by fix would leave one tiny directory per change. Named by area, the documentation accumulates where change actually happens. Its Business Context says it states only the rules changed since, so nobody mistakes it for a full description of the component.
- **With no owning PRD, a business-rule change gets a change PRD; a bug or technical change doesn't.** Those rules otherwise live only in code. The PRD covers its own area; the session never writes a PRD for a whole component.
- **The session writes the change PRD, then follows existing paths.** When it fits one session: the small-PRD path (one review round, and a design only when the design standards call for one), then the build in the same chat, where the investigation's context is. When it is bigger: the standard pipeline from refinement, and `implement-from-requirements` builds it. No new readiness rule was needed.
- **A fix too big for one session is not a change PRD,** because a fix adds no outcome. It is routed the way feedback routes a fix: into the next planned phase nobody has started, or a fix phase at the end of the plan, a fourth kind of completion phase marked `**Added by implement-from-discovery:**`. Completion phases hold criteria the PRD already states, so this does not let discovered work into phases. For the same reason, a technical change too big for one session, and a fix to a component no PRD owns, get a change PRD for their own area instead, the shape `refactor-pass` already gives an oversized refactor: criteria for the behavior kept or restored, and the change in the technical design.
- **Nothing is built beside a running build.** While the owning PRD is mid-build, an amendment its unstarted phases will build is carried forward to them, as a feedback fix is, and a change PRD that would otherwise be built in the same chat waits for that build to close. A fix to a closed phase's criterion, such as a bug blocking the phase in progress, is still built at once.
- **A change PRD gets no early stakeholder review package.** That step exists because a stakeholder asked for the follow-on's work; a discovery change PRD often has no stakeholder behind it. The router and `autonomous-prd-refinement` now limit the early package to follow-ons made from saved stakeholder feedback.
- **Guards against creating change PRDs freely.** A change PRD is only for the change the session was asked to build, at most one per invocation; the lineage gate already stops work the session found for itself, and findings along the way still go through the Materiality Gate. "Only the user creates a change directory" stays as the rule against parking work, with this as its second exception beside the follow-on.
- **The surprise is announced, not asked about.** A request that read like a quick fix can become a change PRD and several sessions. Under requirements first that is the right outcome, but the user should hear it when it is decided, so the line stating the level says so plainly. It is not a stop.
- **The router changed with it.** `using-the-enso-method` sent "the PRD asked for the wrong thing" to an amendment and then `implement-from-requirements` in a new chat, and anything bigger than one session back to the user. Both now go to `implement-from-discovery`, which applies the same sort.
